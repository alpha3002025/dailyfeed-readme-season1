고객사에서 발송 시에 다음 스펙에 따라 429 코드를 리턴할 수 있음 또한 명시합니다.
- Response Code : 429
- Status : Too Many Request
- 발생원인 : 3000/1s 의 Quota 를 넘어섰을 경우

<br/>

이 경우 고객사는 429 Too Many Request 를 받았을 경우 새로고침 주기 이후에 다시 시도하도록 요청하도록 API 가이드 문서에 명시합니다. 이 Rate Limit에서 통과한 요청만 우리 회사의 메시지 발송 API 에 도달하게 됩니다. Spring Cloud Gateway 를 사용할수도 있고, 자유롭게 python,go 등 선택해서 gateway 를 통해 Rate limiter 서버를 앞단에 구현합니다.<br/>


향후 요금제를 등급별로 매겨서 요금제가 높을 수록 발송 허용치의 등급 역시 늘려주도록 할 예정입니다. 우리측 컴퓨팅 자원에 대한 등급 역시 필요해서 추후 이렇게 전환하는 것이 유리해보입니다.<br/>
<br/>

고객사의 메시지를 그대로 받아서 처리해야 하는지, 요청을 무조건 수행하는지를 고려했을때, 이 경우에는 조율을 할 수 있는 영역의 경우로 판단했습니다. 개인적인 경험으로 증권데이터의 경우 거래기록을 우리가 거부할수는 없기에 강제적으로 처리했지만, 고객사 알림톡 대행 서비스의 경우 Rate Limit 을 두어서 요청의 정도를 정량화 할수 있다고 판단해서 제일 앞단엔 Rate Limiter 를 두기로 했습니다.<br/>
