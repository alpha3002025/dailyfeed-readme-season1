

요청 접수 (using kafka publisher)
- 고객사 -> `front-desk` API (+실패시`kafka_publisher_dead_letters`) -> kafka

<br/>

요청 배치 처리
- kafka listener(통신레벨) -> (트랜잭션 레벨) kakaotalk|SMS 발송 처리

<br/>

요청의 배치 처리는 통신레벨, 트랜잭션 레벨에 따라 분류하며, Kafka 의 가용성을 위해 허용한 통신의 모호함은 내부적인 캐시를 통해 통신의 중복수신여부를 체크할수 있습니다. 트랜잭션에서는 유일한 통신메시지 개별 건들을 각각 배치 처리를 합니다. <br/>
<br/>


Listener 에서 메시지 발송시 규칙
- Timeout 은 5분으로 하며, 5분이 지나도 webhook_url 을 받지 못할 경우 해당 요청은 실패 처리
- 실패한 요청은 3번까지 재시도를 수행하며, Batch 의 Timeout, Retryx3 을 모두 실패할 경우 `kafka_listener_dead_letter` 에 해당 요청을 저장
- `통신레벨의 메시지`와 `트랜잭션 레벨의 메시지`를 구분합니다. `통신레벨의 메시지`는 Message Queue 를 통해 흐르는 메시지를 의미하며, `트랜잭션 레벨의 메시지`는 통신 성공 후 DB 에 접근하게 되는 모든 메시지 처리에 대한 비즈니스 요건 처리를 의미합니다.
- (통신레벨 처리) Kafka Listener 는 중복수신을 허용하며, 중복 통신 메시지 여부를 체크해야 합니다. 이에 따라 Kafka message 를 받았다는 표시로 Redis 또는 별도의 캐시 저장소에 key='kafka-listener:listen:${MESSAGE_ID}', value='${START}'를 통해 통신 레벨의 메시지를 기록합니다. 
- (트랜잭션 레벨 처리) 중복 수신이 아닌 새로운 메시지일 경우 트랜잭션 레벨의 작업을 시작합니다. 중복메시지 여부는 key='kafka-listener:listen:${MESSAGE_ID}'가 중복된 메시지 킷값인지 판단을 하는 캐시 저장소를 체크하는 것(통신레벨에서의 메시지 중복체크)으로 수행합니다. 통신레벨의 메시지를 받은 후에는 DB에도 해당 통신 `MESSAGE_ID` 를 기록해야 하는데, `MESSAGE_ID` 는 트랜잭션 처리를 담당하는 테이블의 본키가 메시지 키를 PK(기본키)로 사용할 것이기에, 해당 Key 가 중복수신된 것인지 트랜잭션 레벨에서도 중복체크가 가능합니다.
- (트랜잭션 레벨 처리) Spring Batch 내에서도 작업의 성공여부 상태를 기록하는 기능은 있지만, 메시지에 대한 상태값을 기록하고 모니터링할 수 있어야 하기에 메시지 처리 상태, 일시, 발송수단(`KAKAO|SMS`) 메시지 ID 등을 별도의 테이블에 저장합니다. 발송 시에 메시지의 발송 단계는 'START', 'WAIT', 'SUCCESS', 'FAIL' 로 구분하며, 해당 상태 역시 기록합니다. 메시지 발송 상태 기록 테이블의 이름은 `messaging_log`(가칭... 아직 이름을 못지어서...) 로 합니다.
